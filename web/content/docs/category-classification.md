__ Project UIL__

__ATLAS Taxonomy__

__Document 01 - Category Classification Standard__

__Version 1\.0__

__1\. Purpose__

The Category Classification Standard defines how Human Frictions are organized within the ATLAS Research Repository\.

Its purpose is to ensure that every Human Friction is classified consistently, making the repository scalable, searchable, and easy to maintain as it grows\.

This standard applies to every Human Friction recorded in ATLAS, regardless of when it is added or who contributes it\.

__2\. Philosophy__

Categories exist to organize knowledge-not to limit it\.

A category should answer one question:

__"Where does this Human Friction naturally belong?"__

Categories should represent __domains of human experience__, not technologies, products, or companies\.

For example:

Good Categories

- Files & Folders 
- Authentication 
- Learning 
- Communication 
- Transportation 

Poor Categories

- Google Chrome 
- Windows 11 
- Android 16 
- Microsoft Word 

Products change\. Human experiences last much longer\.

__3\. Classification Principles__

Every category in ATLAS must follow these principles:

__Principle 1 - Human\-Centred__

Categories describe where people experience the friction, not which company or software created it\.

__Principle 2 - Broad but Meaningful__

A category should be broad enough to contain multiple Human Frictions but specific enough to remain useful\.

Example:

 Technology \_Wrong

Web & Browser\_Correct

__Principle 3 - Stable Over Time__

Categories should remain valid even if technologies evolve\.

Avoid names tied to temporary trends or product versions\.

__Principle 4 - Mutually Distinct__

Each category should have a clear purpose\.

Overlap should be minimized\.

__Principle 5 - Scalable__

A category should be capable of holding dozens-or even hundreds-of Human Frictions without becoming ambiguous\.

__4\. Category Hierarchy__

ATLAS follows a four\-level hierarchy:

Domain

    

Category

    

Subcategory \(Optional\)

    

Human Friction

Example:

Digital Experience

    

Files & Folders

    

File Discovery

    

FF\-001

Subcategories are optional and should only be introduced when a category becomes large enough to benefit from additional organization\.

__6\. Category Creation Rules__

A new category may be created only when:

- At least __five__ Human Frictions consistently relate to the same domain __or__ 
- Existing categories cannot accurately describe the new observations\. 

Before creating a new category, researchers should verify that:

- No existing category is suitable\. 
- The category represents a meaningful long\-term area\. 
- The category name is independent of specific products or companies\. 

__7\. Category Naming Rules__

Every category name should:

- Be concise\. 
- Use title case\. 
- Describe a domain rather than a solution\. 
- Avoid abbreviations unless officially defined\. 
- Avoid product or company names\. 

Examples:

__Correct__

__Avoid__

Files & Folders

Windows Explorer

Authentication

OTP Login

Communication

WhatsApp

Learning

Coursera

__8\. Primary Category Rule__

Every Human Friction must belong to __one primary category only__\.

If a Human Friction appears relevant to multiple categories:

- Select the category where the core problem originates\. 
- Use tags or relationships to reference other relevant areas\. 

This ensures each Human Friction has a single authoritative location\.

__9\. Subcategory Rules__

Subcategories should only be introduced when:

- A category contains a substantial number of Human Frictions \(for example, 25-50 or more\)\. 
- Multiple distinct themes emerge within that category\. 
- Additional organization improves discoverability\. 

Example:

Files & Folders



 File Discovery

 File Organization

 File Sharing

 File Recovery

Subcategories are for organization only; they do not receive APIDs\.

__10\. Category Lifecycle__

Every category has one status:

- Proposed 
- Under Review 
- Active 
- Merged 
- Deprecated 
- Archived 

Categories should not be deleted\. If they become obsolete, they should be deprecated or merged while preserving historical references\.

__11\. Category Relationships__

Categories are independent but may be related\.

Example:

Authentication

        

Security

Files & Folders

        

Operating System

Learning

        

Knowledge Management

These relationships support cross\-domain analysis without duplicating Human Frictions\.

__12\. Category Ownership__

Categories belong to the ATLAS taxonomy, not to individual contributors\.

No contributor has exclusive ownership of a category\.

Changes to category definitions should follow the governance process\.

__13\. Future Expansion__

The taxonomy is expected to evolve\.

New categories should emerge from evidence gathered through Human Frictions, not from speculation\.

Growth should reflect observed human experiences\.

__14\. Governance__

Any major change to the taxonomy-such as creating, merging, or renaming categories-must:

- Be documented\. 
- Include a rationale\. 
- Preserve historical consistency\. 
- Update the Prefix Registry and related taxonomy documents\. 

__15\. Final Principle__

__Categories exist to organize understanding, not to constrain it\. Every category should make the repository clearer, more consistent, and more valuable for future research\.__
